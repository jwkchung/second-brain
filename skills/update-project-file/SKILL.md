# Skill: Update Project File

This skill has two callers: you, invoked directly in a conversation when the
user mentions wanting to update, create, or look at a project's file; and
`scripts/nightly-extract-entities.mjs`, which pastes this same file into a
prompt and runs it unattended against newly-archived conversations. Follow
the rules below the same way regardless of which one invoked you.

## When to run this
Run this whenever the user gives an update on an active project, whenever
you pull new information about a project from email, meeting notes, or
documents, or when asked to create a new project file.

## Where the file lives
`<OUTPUT_SUBDIR>/<project-slug>.md` (default: `vault/projects/<project-slug>.md`)

Use a short lowercase slug for the filename (e.g. `website-redesign.md`,
`q3-roadmap.md`). If no file exists for the project yet, create one using
the structure below. If one exists, update it in place, do not create a
duplicate.

## Required frontmatter
Every project file carries this frontmatter:

```yaml
---
type: project
title: <Project Name>
status: active | dormant | closed
aliases: []
---
```

This exists for the same reason the person skill's frontmatter contract
does: anything resolving a wikilink to this project (including the person
and company skills' linking rules) needs a stable slug/alias to match
against instead of guessing. `aliases` is cumulative — append new name
variants as they turn up, never replace. Keep `status` current; it's a
snapshot like "Current status" below, not a log.

## Linking to other entities
When a Key people entry, Decision, or Open question mentions a person or
company that already has its own file, wikilink the first mention of them
(`[[their-slug]]`), using the same no-guessing discipline as the person and
company skills — never create a link to a file that doesn't exist. The
reverse direction (who links to this project) doesn't need maintaining by
hand — that's what your vault tool's backlinks panel is for.

## File structure
Every project file uses these sections, in this order:

```
# <Project Name>

## What it is
One or two sentences. No throat-clearing, no background story. What this project actually is.

## Current status
Where things stand right now. This section gets overwritten as things
change, it is a snapshot, not a log. Do not pile up dated status entries
here.

## Key people
Names and their specific role in this project. Link to their file in the
people output directory if one exists.

## Decisions made
What was decided and why. The reasoning matters more than the decision
itself, this is what prevents re-litigating the same question later. Add
new decisions, do not remove old ones unless they were explicitly reversed
(in which case note the reversal and why).

## Open questions / blockers
What's unresolved. What needs an answer before the project can move. What
should be flagged if it changed.

## Deadlines / key dates
Anything time-bound.
```

## Rules
- Keep "Current status" current. When you update it, replace the old
  status, don't append to it. If the change is significant, you can note
  what changed in one line, but this section should always read as "here
  is where things stand today," not a running diary.
- Never silently overwrite a decision. If new information contradicts
  something already recorded under "Decisions made," flag the contradiction
  explicitly (e.g. "Note: this conflicts with the June decision to do X,
  confirm which is current") rather than deleting the old entry.
- Don't include anything that can be regenerated by searching email or a
  calendar. This file is for things that only exist in someone's head or in
  a specific reasoning chain, not a mirror of an inbox.
- If given a vague or partial update, ask only if you genuinely can't tell
  which section it belongs in. Otherwise make a reasonable call and note
  the assumption.
- The test for whether something belongs in this file: would a smart
  person, cold-reading this file, understand the project well enough to
  help without further explanation from scratch? If a line doesn't clear
  that bar, leave it out.
